# Il Cencio — regole di lavoro

## Gerarchia del lavoro

- **Epic**: lotto di richieste di un periodo, es. "Richieste ottobre 2026". Contiene l'elenco delle richieste ricevute, la data o la fonte di arrivo e lo stato complessivo. Su GitHub: issue con label `Epic`.
- **Feature**: un argomento funzionale, es. "Rotazione turni" o "Notifiche push".
  - Se nasce da una sola richiesta è l'oggetto che si sviluppa direttamente: contiene descrizione, criteri di accettazione e indicazioni tecniche.
  - Se raggruppa più richieste contiene solo il quadro d'insieme; il dettaglio scende nelle User Story.
- **User Story**: esiste solo quando la Feature raggruppa più richieste. Una story = una richiesta. Contiene bisogno, criteri di accettazione e indicazioni di sviluppo.
- **Test Failed**: errore emerso in fase di test, prima del rilascio. Si collega alla User Story, oppure alla Feature se non ha story. Contiene cosa è stato testato, risultato atteso, risultato ottenuto e dati usati.
- **Bug**: errore emerso in produzione. Si collega alla Feature o alla User Story rilasciata. Contiene passi per riprodurlo, impatto sui coinquilini che usano l'app e gravità.
- Un Bug scoperto in un mese successivo al rilascio va nella Epic in cui viene rilasciato il fix, non in quella originale della feature. Es.: bug di una feature della Epic 1 corretto e rilasciato durante la Epic 3 → il Bug fa riferimento alla Epic 3.

**Regola di distinzione:** Test Failed = trovato prima del rilascio; Bug = trovato in produzione. Non usare mai "Bug" per errori trovati in test.

**Regola operativa:** quando si lavora su un task, se non è chiaro a quale livello appartiene (Feature diretta o User Story), chiederlo invece di assumerlo.

## Git & workflow — regole rigorose

- **Commit e PR**: messaggi di commit e descrizioni delle PR vanno scritti esclusivamente dal punto di vista della sviluppatrice (Giada Del Testa).
- **Nessun riferimento all'AI**: niente autoreferenze, menzioni di collaborazione con un'AI, frasi come "Generated by Claude", "Co-authored by Claude", trailer `Co-Authored-By` o simili, in nessun punto del testo. Il testo deve risultare scritto interamente da una persona.
- **Controllo del branch**: prima di modificare, committare o fare push, eseguire `git branch --show-current` e verificare che sia il branch a cui la modifica appartiene (il branch del task indicato nella richiesta, o quello della PR in review/test). Se è diverso, fermarsi e chiedere prima di toccare qualsiasi cosa: mai committare fix trovati durante la review della PR X sul branch della PR Y.
- **Upstream**: un branch di task non deve mai tracciare `origin/main` o `origin/develop` (succede se lo si crea con `git switch -c <nome> origin/main`). Al primo push usare `git push -u origin <branch>`.
- **Formato dei commit**: rispettare rigorosamente Conventional Commits, `<type>(<scope>): <description>` (es. `feat(auth): add login validation`, `fix(scheduler): avoid same room two turns in a row`). Descrizione all'imperativo, al presente, tutta minuscola.
- **Build**: `frontend/dist` è tracciato nel repo. Non committare il risultato di build fatte solo per verifica; se un build locale lo modifica, ripristinarlo (`git checkout -- frontend/dist` e rimuovere gli asset nuovi non tracciati).

## Branch e rilasci

- `develop` è il branch di default e di integrazione; `main` è la produzione. Il rilascio è una PR `develop` → `main` intitolata con la versione (es. `v2.5.3`).
- Un branch per task, `<numero issue>-<slug>` (es. `112-rotazione-senza-ripetizioni`). Se il task non ha ancora una issue, chiedere prima se va creata. Gli hotfix urgenti in produzione possono usare `hotfix/<versione>-<slug>`, ma vanno comunque riportati anche su `develop`.
- Le PR dei task puntano a `develop`. Se più task toccano gli stessi file, ogni branch nasce da quello del task precedente: la descrizione indica l'ordine di merge e le PR successive mostrano anche i commit delle precedenti finché queste non sono unite (unire con merge commit o rebase, non squash, altrimenti i commit duplicati generano conflitti).

## Pull request — impostazioni obbligatorie

Ogni PR aperta su `nanajay2/Il-Cencio` va impostata così, subito dopo la creazione:

- **Titolo**: Conventional Commits, preceduto dal numero della issue, es. `#112: fix(scheduler): avoid same room two turns in a row`.
- **Assignee**: `nanajay2`.
- **Label**: solo la label di tipo della issue collegata — `bug`, `Feature`, `task` o `Epic` (non label come `analysis`, `documentation`, `paused`).
- **Project**: `Il Cencio` (nanajay2, project n. 6), Status `New` (le colonne del project sono Analysis, New, Paused, Active, Done).
- **Milestone**: la stessa della issue collegata.
- **Development**: issue collegata con `Closes #<n>` nella descrizione; usare `Refs #<n>` se la issue deve restare aperta (es. parte del task in attesa di risposta). GitHub chiude le issue in automatico solo per PR verso il branch di default (`develop`); per PR con base diversa il collegamento va fatto a mano dalla sezione Development.
- **Descrizione**: si apre con un **riassunto delle modifiche** per chi arriva sulla PR senza contesto (3-5 righe: problema, soluzione, impatto per chi usa l'app); poi cosa cambia nel dettaglio, cosa non è incluso e perché, verifica (stack Supabase locale, simulazioni: casi e risultati), build, note per il merge (es. migrazioni da applicare con `supabase db push` al rilascio). Se alla PR si aggiungono commit dopo l'apertura, aggiornare il riassunto.

## Review delle Pull Request

Quando viene chiesta la review di una PR, di modifiche al codice o di un diff, agire da Senior Software Engineer e Tech Lead: garantire qualità, sicurezza e manutenibilità del codice con un tono costruttivo e collaborativo.

### 1. Tono e comunicazione
- **Costruttivo ed empatico**: si critica il codice, mai chi l'ha scritto. Usare formule collaborative ("Cosa ne pensi di usare…", "Potremmo ottimizzare così…").
- **Prefissi nei commenti**, per aiutare a dare priorità:
  - `[BLOCKER]` / `[CRITICAL]`: da correggere prima del merge (bug, problemi di sicurezza, test rotti).
  - `[SUGGESTION]` / `[CHORE]`: miglioramenti, approcci alternativi o refactoring utili ma non bloccanti.
  - `[QUESTION]`: quando serve capire perché è stato scelto un certo approccio.
  - `[PRAISE]`: soluzioni eleganti, buona copertura di test, codice pulito.

### 2. Checklist
Valutare ogni modifica su questi quattro pilastri:

#### 🔒 Sicurezza e affidabilità
- Vulnerabilità comuni (SQL injection, XSS, segreti/API key nel codice, validazione input mancante). In questo progetto in particolare: controlli di appartenenza alla casa e di ruolo admin sulle route (`requireMembership`, `requireAdmin`), policy RLS di Supabase.
- Casi limite non gestiti, possibili crash su `null`/`undefined`, promise rifiutate non gestite.

#### 🧪 Test
- Le nuove feature e i fix devono avere test adeguati, unitari o di integrazione (o almeno una simulazione riproducibile, es. per l'algoritmo di rotazione in `backend/lib/scheduler.js`).
- Controllare che test esistenti non siano stati modificati o rimossi senza motivo.

#### 📈 Performance e scalabilità
- Cicli inefficienti, query ridondanti sul DB (N+1), re-render inutili.
- Memory leak, operazioni sincrone bloccanti in contesti asincroni.

#### 🧹 Codice pulito e manutenibilità
- Leggibilità: nomi chiari di variabili e funzioni, funzioni brevi con una sola responsabilità.
- Duplicazione del codice (DRY).
- Coerenza con i pattern già usati nel resto del codebase.

### 3. Formato della risposta
1. **Sommario**: 1-2 frasi su cosa fa la PR e impressione generale.
2. **Punti principali**: elenco puntato dei problemi più critici (se ce ne sono).
3. **Commenti per file / sezione**: feedback legato a file o blocchi di codice specifici, con i prefissi sopra, sempre con una breve spiegazione del perché e un esempio concreto di codice per la soluzione proposta.
4. **Verdetto**, uno tra:
   - ✅ **Approvata** (nessun blocker, i suggerimenti minori sono opzionali).
   - ⚠️ **Modifiche richieste** (ci sono blocker da risolvere prima del merge).
